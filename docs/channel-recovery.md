# 渠道自动恢复

本项目定时检测 NewAPI 后台渠道列表中的故障渠道。必须同时满足两个条件：

| NewAPI 字段 | 条件 |
|---|---|
| `auto_ban`（自动封禁） | `1`，已开启 |
| `status`（状态） | `3`，自动禁用 |

启用中的渠道、手动禁用的渠道，以及关闭自动封禁的渠道都不会被测试或启用。
本项目不新增 `/channels` 页面；查看和编辑渠道仍在 NewAPI 后台进行。

## 管理员设置页

管理员登录后，从仪表盘点击「渠道恢复」，或访问 `/admin/channel-recovery`。
页面提供监控日志，可查看自动禁用原因、禁用时间和每次检测的上游失败提示，并按渠道 ID、检测结果筛选。
监控日志上方提供渠道状态时间轴，每个渠道一行，绿色表示启用、红色表示自动禁用、黄色表示手动禁用、灰色表示未采集或未知。支持 1 小时、24 小时、7 天、30 天缩放，前后浏览历史时段、选择截至时间及按渠道 ID 筛选；悬停或点击色块查看起止时间和持续时长。时间轴独立分页（每页 25 个渠道），不受两组日志的结果筛选影响。
页面可设置开关、检查计划、超时、NewAPI 地址、管理员用户 ID 和访问令牌，并分页查看恢复动作日志，按渠道 ID 和结果筛选。
未登录访客与普通 API Key 用户均不能读取页面、日志或保存设置。

两组日志均在筛选后合并重复记录，每页显示 25 组，按最近出现时间倒序排列。标题分别显示组数和原始记录条数；每组保留出现次数、首次和最近出现时间（以记录创建时间为准）。
监控日志按渠道 ID、结果、禁用原因和检测提示的正文合并；恢复动作日志按渠道 ID、结果和说明正文合并。不同触发方式、试运行状态或恢复动作分别统计，渠道改名不影响合并。
合并覆盖全部匹配记录，不限当前页，也不要求记录连续。比较正文时忽略 `(request id: …)`（含 `request_id` / `request-id` 写法），包括嵌套 JSON 消息里的同类标识；保留状态码、错误内容及其他数字，避免混淆不同故障。
例如，同一渠道在 12:20、12:25、12:30 三次返回 503 `No credentials available`，即使每次请求 ID 不同，也合并为一组，显示 3 次、首次 12:20、最近 12:30。展开保留最后一条完整原文及请求 ID。
渠道名称及其他快照取最后写入的记录；点击时间旁的 `+` 可查看该记录的禁用／完成时间。长内容默认最多两行，悬停查看全文，点击可展开复制。
合并仅改变页面展示，原始日志逐条保留，无需新增数据库迁移。

首次部署本版本时，在**本地 alerts 连接**创建设置和日志表：

```bash
# 已有 alerts.sqlite 时不要替换它，也不要重新生成 APP_KEY
touch database/alerts.sqlite
php artisan migrate --database=alerts --path=database/migrations/alerts
```

PHP-FPM 和 cron 用户需能写入 SQLite 文件及其所在目录。迁移不访问外部 NewAPI 库。

页面保存后，以本地设置为准，下一次调度自动读取，无需清除配置缓存或重启进程。
首次保存前兼容原有 `.env` 配置：

```env
CHANNEL_RECOVERY_ENABLED=true
CHANNEL_RECOVERY_CRON="*/5 * * * *"
CHANNEL_RECOVERY_HTTP_TIMEOUT=30
NEW_API_BASE_URL=https://your-newapi.example
NEW_API_ACCESS_TOKEN=your-admin-access-token
NEW_API_USER_ID=1
```

- 默认关闭，配置完成后开启；默认每 5 分钟一轮，修改 cron 表达式可调整间隔。
- `NEW_API_BASE_URL` 必须与 `DB_*` 指向**同一个 NewAPI 实例**。填站点地址，不加 `/v1` 或 `/api/channel`；支持站点部署路径。
- `NEW_API_ACCESS_TOKEN` 使用 NewAPI 管理员账号的个人访问令牌，`NEW_API_USER_ID` 为该账号的数字 ID。模型调用用的 `sk-...` 令牌不能替代管理员访问令牌。
- 管理账号需要读取、测试和更新渠道状态的权限；传统更新接口还需要渠道编辑权限。
- 外部数据库账号仍然只需要 `SELECT` 权限，需能读取 `channels.id`、`channels.name`、`channels.status`、`channels.auto_ban`、`channels.priority`、`channels.weight`。新增表只在本地 SQLite 中。
- 访问令牌使用现有 `APP_KEY` 加密保存，页面不回显，也不在验证失败时放入 session。留空保留现有令牌；勾选清除必须同时关闭自动恢复，清除后不会回退到环境令牌。
- 页面保存过后，修改上述 `.env` 值不会覆盖页面设置，包括启停开关。此时请通过页面修改。

若通过 `.env` 配置，先执行 `php artisan config:clear`。配置完成后可试运行：

```bash
php artisan channels:recover --dry-run
php artisan schedule:list
```

`--dry-run` 会实际测试渠道并保存标记为「试运行」的监控日志，但不会启用或生成恢复动作日志。测试可能消耗上游额度，NewAPI 也可能更新测试时间、响应耗时并记录测试日志。
检查通过后可手动恢复一轮：

```bash
php artisan channels:recover
# 只处理指定渠道，仍须满足 auto_ban=1 且 status=3
php artisan channels:recover --channel-id=7
php artisan channels:recover --channel-id=7 --dry-run
```

服务器需配置 Laravel 调度器（与额度预警共用，已有则无需重复添加）：

```cron
* * * * * cd /path/to/newapi-log && php artisan schedule:run >> /dev/null 2>&1
```

`schedule:list` 中会显示每分钟执行 `channels:recover --scheduled`，命令再根据页面保存的 Cron 计划和应用时区判断是否到期。
页面开关关闭或尚未到检查时间时，不访问外部数据库和 NewAPI 接口。手动命令遵守开关，但不等待计划到期。

cron 使用与 PHP-FPM 相同的用户。默认文件缓存支持防重入锁；多实例部署时需共享支持锁的缓存及同一份本地设置与日志，避免不同机器各自检查。
关闭功能时在页面取消「开启渠道自动恢复」并保存；正在执行的一轮会继续完成。

## 检查与恢复流程

1. 从只读数据库分批采集所有 `auto_ban=1` 渠道的 ID、名称与状态，保存到本地时间轴采样表；再按 ID 分批取出自动禁用的渠道，读取管理接口再次确认状态。在本地保存自动禁用快照（渠道 ID、名称、禁用原因和禁用时间）。
2. 调用 `GET /api/channel/test/{id}`。由 NewAPI 使用渠道自身的测试模型及协议适配器发起真实请求；只接受 HTTP 成功且 JSON 中 `success` 严格为 `true` 的结果。将检测结果及上游提示写入监控日志，失败和异常也会保留。
3. 先在本地写入恢复动作日志，再重新读取渠道。检测期间若已手动禁用、已启用或关闭自动封禁，则跳过状态更新。
4. 调用 NewAPI 的状态更新接口恢复到 `status=1`，让 NewAPI 更新路由能力和缓存；随后再次读取，确认已启用才计入“已恢复”。本项目不直接写外部数据库。

新版优先使用 `POST /api/channel/{id}/status`，只发送 `status`。
若该接口明确返回 HTTP 404/405，则重新核对渠道条件，并使用传统的 `PUT /api/channel/`，只发送 `id` 和 `status`。
鉴权失败、业务失败和超时不会触发降级或重复写入。
接口依据：[官方渠道管理文档](https://doc.newapi.pro/api/fei-channel-management/)、[新版渠道路由源码](https://github.com/QuantumNous/new-api/blob/main/router/channel-router.go)。

测试失败或请求异常时不启用该渠道，继续处理其他渠道，下个周期重新检查。
不支持 NewAPI 单渠道测试的渠道类型会保留原状态；多密钥渠道整体仍须是 `status=3`，不会扫描或解封单个密钥。
“恢复正常”以该渠道的测试模型成功为准，并不代表渠道配置中的每个模型都已恢复。

任务使用锁避免定时与手动执行重叠，上一轮未完成时不会启动重复检查。
上游状态更新接口不支持原子条件更新，最后一次读取与更新之间仍有并发窗口；进行人工批量维护时可先停用定时恢复并等待当前轮结束。

## 检查结果

命令输出检查数、测试正常数、已恢复数、因状态变化跳过数和失败数；有失败时返回非零退出码。
`storage/logs/laravel.log` 记录每次成功恢复的渠道 ID、失败阶段及每轮汇总；接口异常可包含脱敏后的提示文字，不保存原始接口响应。

### 最近一轮检查

管理员页顶部显示最近一轮实际执行的检查（本地 `channel_recovery_runs` 表，只保留一行）：开始时间、触发方式、各项计数，
以及每个失败渠道的阶段和提示（最多 20 条），配置无效或查询渠道失败等整轮错误也会显示。
读取渠道详情失败时不会生成监控日志，此前只能在 `laravel.log` 中看到；NewAPI 地址、访问令牌或用户 ID 填错时，先看这里。
开关关闭、计划未到期或因已有检查在运行而被拒绝的调用不会覆盖这一行；开始后超过 1 小时仍未结束则提示进程可能已中断。
状态写入失败只记服务日志，不影响检查与恢复本身。

### 渠道状态时间轴

更新后执行上述 alerts 专用迁移，新增本地 `channel_status_samples` 表。每轮实际执行的检查采集 `auto_ban=1` 渠道，包括已启用与手动禁用的渠道，仅查询状态，不对这些渠道发起测试或恢复。试运行也保存状态采样；指定 `--channel-id` 时只采集该渠道。关闭开关或检查计划未到期时不采集。

渠道在分页之前按优先级降序排列，同优先级按权重降序排列，两者相同时按渠道 ID 升序排列。排序使用最近一次监控采集的配置，查看历史时段也采用该顺序。优先级和权重保存在本地 `channel_monitor_metadata` 表，每个渠道保留一条最新记录；更新后需执行上述 alerts 专用迁移，并等待下一轮检查采集排序信息。历史渠道暂未采集排序信息时保留展示，排在已采集的渠道之后。

图表由本地状态采样、原始监控日志及已确认恢复的动作日志生成；查看页面不访问外部 NewAPI 数据库或管理 API。新状态采集失败会在「最近一轮检查」显示提示，已有恢复流程继续执行。

状态采样保留到下一次计划检查后 1 分钟，连续同状态时段合并显示；超过此时间仍无新观察则显示灰色，避免服务停止或关闭采集后仍一直显示正常。每条采样的有效期在采集时保存。历史监控日志与恢复动作没有采样有效期，按当前检查计划估算。

自动禁用优先采用有效的 `disabled_at`，但旧禁用时间不会覆盖之后已确认的其他状态。测试结果为「正常」或试运行不代表已启用；只有状态采样为启用，或恢复动作 `recovered` 且已完成并确认启用，才显示绿色。手动禁用单独显示黄色。

采集前的历史在线状态无法补全，显示灰色。两轮之间发生并结束的状态变化可能无法观察到；「正常 / 启用」表示渠道状态已启用，不代表其所有模型均已通过健康检测。状态采样及日志都保存在本地 alerts 库，随该库一起备份。

### 监控日志

监控日志保存在本地 alerts 连接的 `channel_monitor_logs` 表，部署更新后须执行前述 alerts 专用迁移。
每轮实际检查中，经管理接口确认仍满足 `auto_ban=1`、`status=3` 的渠道都会生成一条记录，包括试运行。
同一渠道持续禁用时，每轮保留独立记录，方便比较失败原因的变化；不把多次检查误认为多次禁用。

- **发现时间**是本项目检查发现自动禁用的时间；**禁用时间**取渠道详情 `other_info.status_time`（Unix 秒数），缺失或无效时显示未提供。
- **自动禁用原因**取 `other_info.status_reason`，兼容 `other_info` 为 JSON 字符串或对象。它是测试前的快照，恢复后仍可查看。字段来源见 [NewAPI 渠道状态源码](https://github.com/QuantumNous/new-api/blob/main/model/channel.go)。
- **本次检测提示**保存测试接口的 `message`、`error.message` 或字符串 `error`；非成功 HTTP 响应也会提取文字提示。它与最初的禁用原因分别展示。
- 不保存整份接口响应；提示文字写入前屏蔽已知管理员令牌、详情中可用的渠道密钥及常见认证格式，并限制长度。页面按纯文本转义展示。
- 测试失败但没有提示时显示「上游未提供失败原因」；超时/连接失败显示通用原因，HTML 等非 JSON 响应仅记录接口异常。

| 检测结果 | 含义 |
|---|---|
| 待检测 / 未完成 | 已保存禁用快照，尚无检测结果；任务中断或日志更新失败时会保留 |
| 测试正常 | 测试接口明确返回成功；实际恢复结果查看恢复动作日志 |
| 测试失败 | 测试接口明确返回失败，可查看上游提示 |
| 检测异常 | 超时、连接失败、HTTP 错误或接口格式无效 |

采集遵守自动恢复开关和检查计划。日志从部署并执行检查后开始积累，不补采历史事件；两轮之间禁用后又恢复的短暂事件可能无法观察到。
监控日志只记录已自动禁用的整个渠道，范围与自动恢复一致。监控日志写入失败时不会开始测试或恢复；记录仅管理员可见，独立分页与筛选。

### 恢复动作日志

管理员页的恢复动作日志持久化在 `channel_recovery_logs`（本地 alerts 连接），包含渠道 ID、渠道名称快照、
发起和完成时间、定时/手动来源、原状态与目标状态，以及结果。只记录测试通过后的恢复尝试，试运行、未通过的检测不产生恢复动作日志。

| 结果 | 含义 |
|---|---|
| 已恢复 | NewAPI 返回成功，且再次读取确认已启用 |
| 已跳过 | 恢复前条件已变化，未发起状态更新 |
| 恢复未确认 | 更新或后续确认失败；例如超时后可能已在上游生效，需核对实际状态 |
| 处理中 / 未完成 | 恢复意图已记录，尚未完成；进程中断或日志最终写入失败也会保留此状态 |

日志写入失败时不会开始恢复；已发起的远端请求和本地日志不属于同一个事务，因此以 pending 记录保留未完成动作，不能把它当作成功。
日志保留在 SQLite 中，不自动清理；备份须同时保存 `database/alerts.sqlite` 与原 `APP_KEY`，以便解密访问令牌。

| 情况 | 排查 |
|---|---|
| 没有定时检查 | 确认页面开关已开启、检查计划到期、系统 cron 存在；用 `schedule:list` 检查注册结果 |
| 设置页报缺少表 | 执行上面的 alerts 专用迁移命令，不要运行无参数的 migrate |
| 已保存的令牌无法读取 | 检查是否改变了 APP_KEY；恢复原 APP_KEY 或在页面重新填写令牌 |
| 检查数为 0 | 确认渠道同时满足 `auto_ban=1`、`status=3`；手动禁用不会检查 |
| 读取接口失败 | 管理员页「最近一轮检查」会显示「读取渠道详情」失败；检查 NewAPI 地址（须是 NewAPI 本身，而不是本站）、管理员访问令牌、用户 ID 和读取权限 |
| 测试失败 | 在 NewAPI 后台用同一测试模型测试，检查上游状态、额度和模型配置；必要时调整超时 |
| 测试正常但未恢复 | 查看是否因状态变化跳过；检查状态更新权限、接口版本，以及更新后的实际状态 |
| 提示已有检查运行 | 等当前轮完成；异常退出留下的锁最多保留 24 小时，仅在确认没有任务运行后清理应用缓存 |
